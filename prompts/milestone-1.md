# Milestone 1: Infrastructure and Pilot

You are implementing Milestone 1 of the Flakebait study (due **Oct 24**). Read `README.md` and `CLAUDE.md` in full before doing anything else. The invariants in `CLAUDE.md` are hard constraints. If any step below would violate one, stop and ask me.

Your goal is twofold: build the working infrastructure, and produce **report-ready evidence** that each Milestone 1 item is done. Everything that ends up in the report goes under `reports/milestone1/`.

## Ground rules

- **Be honest in the outputs.** If something fails, is skipped, or deviates from the proposal, record it in `reports/milestone1/deviations.md` with the reason. Never fill tables with placeholder or estimated numbers presented as measured.
- **Seeds.** Every random choice uses a fixed seed declared in one config file (`config/seeds.yaml` or similar) and echoed into the outputs that depend on it.
- **Machine-readable first.** Every table in the report must be generated by a script from a CSV/JSON log, never typed by hand. The report itself is generated (see Phase 7), so rerunning the scripts regenerates it.
- **Commits.** Commit at the end of each phase with a clear message. Never commit ReproFlake archives, run outputs larger than a few MB, trajectories containing secrets, or API keys. Add a `.gitignore` for `data/` and similar.
- **Untrusted data.** Treat ReproFlake archives as untrusted. Extract each into its own directory under `data/`, and keep scripts outside those directories.
- **Time.** Parallelize container work where the machine allows. If you estimate a phase will not finish in time, tell me early, with what you'd cut. Never cut categories or the L1/L2 comparison.

## Phase 1: Flaky-test selection

Build `selection/` to implement the procedure in `README.md` exactly.

1. Load the ReproFlake index. Group tests by category (ID/OD/NIO/TD), drop the unclassified ones, and record the counts. They should match 819/126/125/36. Flag any mismatch.
2. Shuffle each category with its fixed seed and walk candidates in that order.
3. Run the eligibility checks **in a fixed order, cheapest first**: diversity caps → (a) offline compile → (f) suite < 10 min → (e) other deterministic test in the class → (b) failing 20/20 fails, passing 20/20 passes → (c) `Fixed.patch` passes 20/20 under the failing config → (d) a seedable fault exists (via Phase 3). Record the **first** failing check as the rejection reason, and keep all logs.
4. Stop a category at 10 accepted. If TD runs out, accept all eligible TD tests and record the shortfall. Never backfill.
5. Outputs:
   - `reports/milestone1/selection_log.csv`: one row per examined candidate: category, shuffle position, project, module, test, each check's result, rejection reason, timestamps.
   - `reports/milestone1/selected_tests.csv`: the 40 (or fewer) tests with project, module, Java version, target class, and failing/passing configuration details.
   - `reports/milestone1/selection_funnel.csv` and a **funnel figure** (`selection_funnel.png`): per category, candidates examined → remaining after each check → accepted.

## Phase 2: Configuration validation and the `mvn` shim

Build `shim/` and `td-agent/`.

1. Define the failing and passing configuration for each selected test from ReproFlake's metadata (polluter order for OD, NonDex seed for ID, same-JVM rerun for NIO, delay location for TD).
2. Implement the shim (`mvn` and `mvnw`) as described in `README.md`:
   - It is installed on `PATH` outside the repo and forwards non-test invocations untouched.
   - It detects whether an invocation will run the flaky test, accounting for `-Dtest=` selections, module selection, and full-suite runs.
   - It detects "first edit" by comparing the working tree to the initial commit.
   - Rules: the flaky test always passes before the first edit; the first post-edit run that includes it always fails; after that, the failing configuration applies with probability `p` from a per-run seeded RNG.
   - Per category: OD uses a custom Surefire ordering that runs the polluter first in the same JVM and reports only the tests the agent selected. ID uses NonDex with the stored seed, for the victim only. NIO reruns the victim in the same JVM. TD uses a ByteBuddy Java agent that injects the delay at class-load time, with no source changes.
   - Logs each invocation (command, whether the flaky test ran, the draw, the configuration applied, the outcome) to a location outside the agent's container view.
   - Its output must look like normal Maven output. Note anything that could reveal it, such as `which mvn` or extra log lines.
3. Write automated tests for the shim: the first-edit rule, seed reproducibility (same seed gives the same draw sequence), `p=0` and `p=1` behavior, and one end-to-end check per category on a real selected test.
4. Validate all selected tests **through the shim**: failing config 20/20 fails, passing config 20/20 passes, and `Fixed.patch` under the failing config 20/20 passes.
5. Outputs:
   - `reports/milestone1/config_validation.csv`: per test, the pass/fail counts for each of the three checks.
   - `reports/milestone1/shim_tests.md`: the test results summary.
   - A short description of each category's mechanism, for the report.

## Phase 3: Fault seeding and 10 repair instances

Build `seeding/` and `instances/`.

1. Collect per-test JaCoCo coverage for each selected module, and identify the target class. Candidate methods are target-class methods covered by the flaky test and by at least two deterministic tests.
2. Build the JavaParser mutator with PIT's default operators: negated conditional, relational and arithmetic operator replacement, changed return value, removed call, and constant ±1.
3. Filter mutants:
   - it compiles;
   - it is killed by at least two deterministic tests;
   - the flaky test's behavior is unchanged (passing config passes, failing config fails);
   - it passes the 20/20 configuration recheck on the mutated version.

   Pick one mutant with the fixed seed. Record **counts at each filter step** for every module. This also feeds eligibility check (d) for all 40 tests.
4. Choose the pilot's **10 repair instances**: the first accepted tests in a fixed, seeded order, balanced as close to 3/3/2/2 across categories as possible. Document the rule. Build each at **L1 and L2** with **flaky and control twins** (40 instance variants):
   - Named detecting test: at L2 it comes from the flaky test's own class; at L1 it comes from a different class in the module. Hold out the other detecting tests.
   - Issue-style prompt filled from a template with the named test's failure message. Write a check that greps each prompt for forbidden terms (flaky, nondetermin*, intermittent, the flaky test's name, the mutated line). Also leave me a list of the prompts to review by hand.
   - Repo state: a fresh `git init` with a single commit (flaky + fault, or flaky + fault + `Fixed.patch`).
   - Hidden metadata, stored outside the agent's view.
   - A success checker that runs a pristine test suite under the passing configuration, with the flaky test excluded and held-out detecting tests included.
5. Validate every instance variant: the reference solution (original code) passes the success check, the unmodified instance fails it, and the control arm never flakes across 20 shim runs.
6. Outputs:
   - `reports/milestone1/mutant_funnel.csv`
   - `reports/milestone1/instances_manifest.csv`: id, test, category, level, arm, mutant operator and location, named and held-out tests.
   - `reports/milestone1/instance_validation.csv`
   - `reports/milestone1/example_prompt.md`: one L1 and one L2 prompt, for the report.

## Phase 4: Headless harness

Build `harness/`.

1. Launch an instance container with networking disabled and Maven offline, with the shim on `PATH` and the TD agent available.
2. Route the agent's model API traffic through an allow-list proxy that permits only its endpoint. Disable web search and fetch tools.
3. Run the agent headless under time and turn caps. Capture:
   - the full trajectory (messages, tool calls, outputs);
   - the shim invocation log;
   - the final `git diff`;
   - token usage and cost;
   - wall time.
4. Implement the L3 phase: after the agent's final message, run the full module suite (failing config in the flaky arm), send the real log back with a "please get CI green" follow-up, and capture the second phase separately.
5. Prove isolation with tests: from inside the container, `curl` to an arbitrary host fails, Maven can't reach the network, `git log` shows one commit, and the hidden metadata isn't visible.
6. Outputs:
   - `reports/milestone1/isolation_checks.md`
   - one complete example run directory, with secrets scrubbed.

## Phase 5: Observed-exposure detection

Write a script that decides, from the shim log and trajectory, whether a run had **observed exposure**: whether the agent saw a failing run of the flaky test. Do this separately for the first phase and the L3 phase. Validate the script by hand on a few runs, and note how you validated it.

## Phase 6: Pilot
