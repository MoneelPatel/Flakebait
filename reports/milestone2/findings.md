# Milestone 2: main study, preliminary findings

The tables are in `main_results.md` (generated by `flakebait/analysis.py` from `main_runs.csv`). These are
preliminary: the judge's labels have not yet been checked against human annotation (Milestone 3), TD rests on a
single test, and every run is at exposure level L2 with the neutral prompt.

## What ran

- **Runs.** 168 runs: 28 flaky tests (ID 10, OD 7, NIO 10, TD 1) x 2 arms (flaky, control) x 3 repetitions,
  with Codex CLI 0.163.0 on GPT-6 Luna. Every fault is an LLM-written bug with an issue report (deviation #32).
  OD and NIO use the category-faithful shim (#33).
- **Cost.** The agent cost $3.73 (mean $0.030 per flaky run, $0.015 per control run). The study's total spend
  is $5.56, which also covers bug and issue writing and the judge. No run hit the time cap.
- **Excluded.** The 6 runs of the mybatis ID test are excluded: the build rewrites source files in 2026,
  which broke both the shim's reproduction and the success check (#37). 162 runs remain.

## Findings

1. **The agent almost always solves the task, but the flaky failure costs it.** In the control arm, the task
   succeeds in 81/81 runs, and only 2 runs hit the 30-call turn cap. In the flaky arm, 79/81 runs succeed after
   the main phase, but only 74/81 still succeed after L3. 26/81 flaky runs (32%) hit the turn cap (NIO 15/30),
   and a flaky run costs twice as much as a control run.

2. **How the agent runs tests decides OD exposure.** With the faithful shim, an OD test fails only when its
   polluter (another class) runs first in the same JVM. At L2 the agent runs the named class alone, so OD was
   observed failing in the main phase in only 3/21 runs, against 24/27 for ID, 27/30 for NIO and 3/3 for TD. In
   the L3 CI run of the full module, OD was exposed in 21/21 runs. Before the faithful shim, the Milestone 1 shim
   reported exposure regardless of how tests were run. Answering the feedback, this is the cost of realism.

3. **RQ1: the agent usually recognizes the failure as unrelated** (judge labels, on runs where the failure was
   observed). It did so in 45/57 exposed main phases (79%) and in 60/66 exposed L3 phases (91%). It reported the
   failure in its final message in 70/78 exposed runs (90%). It reran or isolated the test to check whether the
   failure was real in 43/78 runs: 27/30 for NIO, but only 8/24 for ID and 8/21 for OD.

4. **RQ2: most often it fixes the flaky test, not just leaves it alone.** Final outcomes of the 78 exposed flaky runs:
   (a) root-cause fix in 58 (74%), (b) left alone and reported in 11, (c) left alone and unreported in 1,
   (d) masked in 2, (e) damaging in 6.
   - **Fixes are verified.** Every (a) passed 3/3 reruns of the validated failing configuration on the agent's
     final tree. Most are test-side fixes in the flaky test's class (order-insensitive comparisons, resetting
     state) or, for OD, cleanup in another test class. Two ID instances got production fixes in the code under
     test: iterating enum constants in declaration order (typescript-generator), and sorting before printing
     (json-schema). This was checked by hand on samples.
   - **This is not the behavior the proposal expected.** The agent rarely ignores the failure; it treats it as a
     second task. Whether it should change tests nobody asked it to touch is what the `locked` variant (RQ4)
     measures.

5. **The damage is collateral: the agent undoes its own correct fix.** All 6 (e) runs (NIO 5/30, OD 1/21) were
   solved after the main phase. In L3 the CI log showed the flaky failure, and the agent changed its bug fix
   while chasing it, so the task failed on the pristine suite. The judge says the agent blamed its own change in 3
   of these runs. In every one it reported the failure, so under the current definition there is **no silent
   damage** (0/78). The control arm has no (e) runs.

6. **Masking is rare and ambiguous.** Both (d) runs, and the only (d) in the control arm, come from the same
   instance (elastic-job OD): the agent excluded the `All*Tests` suite classes in `pom.xml`. That keeps
   suites from rerunning every test, but it is also build configuration that hides tests. Human annotation will
   decide. No run ignored, deleted or retried the flaky test.

## Problems found, and what changes

- **A stored NonDex seed is sensitive to code changes.** ID's failing configuration replays a recorded NonDex
  seed. After the agent's edits, that seed no longer failed for one test (ServiceComb, never exposed in any run).
  It also stopped failing in L3 for others whose fix did not touch the ordering. Because of this, ID exposure is
  measured (observed exposure), not assumed. For the report: a seed-based reproduction validated on the original
  code is not a stable failing configuration for the code the agent writes.
- **The judge flags failures that did not happen.** In 4 control runs, the judge said the test of interest
  failed when it did not. Three are the same NIO instance, where the bug makes 11 tests in the flaky test's class
  fail and the judge counted the flaky test among them. The tables therefore take every denominator from observed
  exposure, never from the judge. Before annotation, the guide will say that the test failed only when the output
  names it as failing; these runs go first into the annotation sample.
- **The harness's CI run must not change the agent's tree.** It now restores it (#37).

## Local open-weight arm (gpt-oss:20b): no usable results yet

The 18 runs (`local_runs.csv`, `local_results.md`: 9 pilot tests x 2 arms, L2, 1 repetition, about 4.5 hours)
ran without harness errors. They measure an integration failure, not the model's behavior:

- No run made a single file edit, and no run solved the task.
- Most model calls failed. Whenever gpt-oss:20b tried to edit a file, it emitted an `apply_patch` call (a heredoc
  inside the JSON arguments) that Ollama 0.40.13 could not parse, and Ollama answered HTTP 500 ("error parsing
  tool call"). Codex retried, each retry counted against the 30-call cap, and every phase ended at the cap or with
  a stream error. Codex also warns that it has no model metadata for `gpt-oss:20b`.
- The two (e) outcomes in that table are artifacts of the same failure. All rows are reported, none are
  interpreted.

The meter, isolation, shim and scoring all worked with a local model. What breaks is the model server's
tool-call parsing. Options: a server whose gpt-oss tool parser handles these calls (a newer Ollama, vLLM, or
LM Studio), or a different open-weight coding model with native tool calling. Each needs a smoke run first.
